# การประยุกต์ใช้ ISO/IEC 29110

เอกสารนี้กำหนดวิธีนำ ISO/IEC 29110 มาใช้กับโครงการ No.1 Sports โดยเลือกแนวทาง
**Basic Profile สำหรับโครงการพัฒนาซอฟต์แวร์ของหน่วยงานขนาดเล็ก (VSE)** ให้เหมาะกับทีม
และระบบที่มีอยู่จริง เอกสารนี้เป็นแนวทางปฏิบัติและหลักฐานของโครงการ ไม่ใช่การรับรอง
มาตรฐานจากหน่วยงานภายนอก

**ฉบับ:** 1.0  
**สถานะ:** ใช้เป็นแนวทางปฏิบัติ  
**ขอบเขต:** เว็บจองสนามฟุตบอล Vue 3, PHP API, MySQL และการติดตั้งบน XAMPP/โฮสติ้ง

## 1. เป้าหมายและขอบเขต

โครงการต้องส่งมอบระบบที่ลูกค้าสามารถเลือกสนามและเวลา จอง ชำระเงินด้วยการแนบสลิป
รับตั๋ว QR และเช็คอินได้ ส่วนผู้ดูแลต้องจัดการสนาม ราคา โปรโมชั่น การตรวจชำระเงิน
และสถานะการเข้าใช้สนามได้อย่างปลอดภัย

ไม่อยู่ในขอบเขตของรุ่นนี้: การยืนยันอีเมลหรือ SMS OTP, การเชื่อมธนาคารอัตโนมัติ,
การตรวจสลิปอัตโนมัติ, การคืนเงินอัตโนมัติ และการทดสอบกล้องบนอุปกรณ์จริง

## 2. กระบวนการที่ใช้

ใช้สองกระบวนการของ Basic Profile ดังนี้

| กระบวนการ | การใช้กับโครงการ | ผลลัพธ์หลัก |
| --- | --- | --- |
| Project Management (PM) | วางแผน ติดตามความคืบหน้า ควบคุมความเสี่ยงและการเปลี่ยนแปลง | แผนโครงการ, บันทึกความคืบหน้า, บันทึกความเสี่ยง, คำขอเปลี่ยนแปลง, บันทึกการประชุม, บันทึกการยอมรับ |
| Software Implementation (SI) | วิเคราะห์ความต้องการ ออกแบบ พัฒนา ทดสอบ ส่งมอบและบำรุงรักษา | ข้อกำหนด, แบบจำลอง/การออกแบบ, ซอร์สโค้ด, ผลตรวจสอบ, ผลทดสอบยืนยัน, คู่มือ, รุ่นที่ส่งมอบ |

วงจรงานของโครงการเป็นแบบเพิ่มทีละส่วน: วางแผน -> วิเคราะห์/ออกแบบ -> พัฒนา -> ตรวจสอบ
และยืนยัน -> ทดลองรับมอบ -> ปล่อยใช้งาน -> บำรุงรักษา โดยแต่ละรอบต้องมีหลักฐานใน
Git และเอกสารส่วนนี้อัปเดตตามจริง

## 3. บทบาทและความรับผิดชอบ

| บทบาท | ผู้รับผิดชอบ | หน้าที่หลัก |
| --- | --- | --- |
| Project Manager (PM) | เจ้าของโครงการ/ผู้ดูแลหลัก | อนุมัติขอบเขต แผน ความเสี่ยง การเปลี่ยนแปลง และการส่งมอบ |
| Customer/Business Owner | เจ้าของสนาม | ยืนยันกฎการจอง ราคา โปรโมชั่น ขั้นตอนชำระเงิน และผลการรับมอบ |
| Developer | ผู้พัฒนา | วิเคราะห์ ออกแบบ แก้ไขโค้ด ทบทวน และดูแล migration/configuration |
| Tester/Reviewer | ผู้พัฒนาหรือผู้ตรวจที่ PM มอบหมาย | รัน test ตรวจความปลอดภัย ตรวจ acceptance criteria และบันทึกผล |
| Operations/Admin | ผู้ดูแลระบบ | ติดตั้ง สำรองข้อมูล ตั้ง maintenance และตรวจการทำงานหลังปล่อย |

บุคคลเดียวอาจทำหลายบทบาทได้ แต่การยืนยันรับมอบต้องมี Customer/Business Owner
เป็นผู้อนุมัติแยกจากผู้พัฒนาเมื่อทำได้

## 4. แผนโครงการ (PM.PLAN)

### 4.1 งานและผลส่งมอบ

| ระยะ | งาน | หลักฐาน/ที่เก็บ |
| --- | --- | --- |
| กำหนดความต้องการ | ยืนยันผู้ใช้ บทบาท กฎการจอง การชำระ และการเช็คอิน | ส่วนที่ 5 ของเอกสารนี้, issue หรือบันทึกประชุม |
| ออกแบบ | ออกแบบ flow, API, schema, สิทธิ์ และการจัดการข้อผิดพลาด | `src/`, `server/`, `database/schema.sql`, code review |
| พัฒนา | แก้ไขโค้ดและ migration ตาม issue ที่อนุมัติ | Git commit และ pull request/code review |
| ตรวจสอบ | รัน build, syntax check, API/integration test และ security checks | `npm.cmd test`, `npm.cmd run build`, ผลตรวจใน CI/บันทึก release |
| ยืนยันและส่งมอบ | ทดสอบเส้นทางลูกค้าและแอดมินด้วยข้อมูลทดสอบ แล้วอนุมัติปล่อย | ส่วนที่ 8 และ `release/README.md` |
| ปฏิบัติการ | สำรองข้อมูล ตั้ง cron และตรวจ health หลังปล่อย | log, backup record และ maintenance record |

### 4.2 เกณฑ์ความสำเร็จ

- ฟังก์ชันในขอบเขตผ่าน acceptance criteria ที่อนุมัติแล้ว
- `npm.cmd test` และ `npm.cmd run build` ผ่านก่อนสร้าง release
- PHP syntax และ database test ผ่านบนสภาพแวดล้อมทดสอบ
- ไม่มี defect ระดับวิกฤตหรือสูงที่ยังไม่ถูกยอมรับเป็นความเสี่ยง
- การติดตั้งใหม่ทำตาม README ได้ และมีการทดสอบเส้นทางจองตั้งแต่ต้นจนจบ
- มีผู้รับผิดชอบและหลักฐานสำหรับ backup, session storage, HTTPS และ cron maintenance

และการยอมรับ

## 6. การออกแบบและการตรวจสอบ (SI.2-SI.3)

### 6.1 จุดควบคุมการออกแบบ

- Vue รับผิดชอบการแสดงผลและการโต้ตอบ ส่วน PHP API เป็นผู้ตัดสินสิทธิ์ สถานะ และราคา
- MySQL ใช้ InnoDB, foreign key และ transaction เพื่อป้องกันข้อมูลการจองขัดแย้ง
- session/CSRF/password hash/file validation อยู่ในชั้น server และไฟล์สลิปอยู่นอก web root
- ทุกการเปลี่ยนสถานะสำคัญของแอดมินต้องมี audit log
- การเปลี่ยน schema ต้องมี migration ที่ทดสอบกับฐานข้อมูลว่างและฐานข้อมูลเดิม

### 6.2 รายการตรวจสอบก่อนรวมโค้ด

- [ ] ผูกการแก้ไขกับ requirement หรือ issue ที่ชัดเจน
- [ ] ตรวจสิทธิ์, CSRF, input validation, SQL injection และการเปิดเผยข้อมูล
- [ ] ตรวจกรณีซ้ำ/พร้อมกัน/หมดเวลา/เครือข่ายล้มเหลว
- [ ] เพิ่มหรือปรับ automated test เมื่อพฤติกรรมเปลี่ยน
- [ ] รัน `npm.cmd test`, `npm.cmd run build` และ PHP/database checks ที่เกี่ยวข้อง
- [ ] อัปเดต README, migration หรือ release notes เมื่อผู้ติดตั้งได้รับผลกระทบ

ตารางนี้เป็นทะเบียนขั้นต่ำของหลักฐาน ต้องอัปเดตเมื่อเพิ่ม requirement หรือ test

## 8. การยืนยันและรับมอบ (SI.5-SI.6)

ผู้ทดสอบต้องบันทึกวันที่ สภาพแวดล้อม commit/release ข้อมูลทดสอบ ผลที่คาดหวัง
ผลจริง และ defect ที่พบ สำหรับรอบรับมอบอย่างน้อยให้ทำตามลำดับนี้:

1. สมัครหรือเข้าสู่ระบบด้วยบัญชีลูกค้าทดสอบ
2. เลือกสนาม วัน และเวลา แล้วสร้างรายการจอง
3. ตรวจยอดจากเซิร์ฟเวอร์ แนบสลิปทดสอบ และตรวจสถานะรอตรวจ
4. เข้าบัญชีแอดมิน ตรวจยอด ยืนยันการชำระ และตรวจว่าตั๋ว QR ถูกสร้าง
5. ใช้ QR หรือรหัสตั๋วเช็คอิน ตรวจการป้องกันเช็คอินซ้ำ และจบการใช้สนาม
6. ตรวจ audit log, สิทธิ์การเข้าถึง, กรณีจองซ้ำ และรายการหมดเวลา

### แบบบันทึกผลรอบรับมอบ

| รายการ | ค่า |
| --- | --- |
| Release/commit | เติมก่อนทดสอบ |
| วันที่และผู้ทดสอบ | เติมก่อนทดสอบ |
| สภาพแวดล้อม | PHP, MySQL/MariaDB, browser, OS |
| ผลรวม | ผ่าน / ไม่ผ่าน / ผ่านโดยมีเงื่อนไข |
| Defect ที่ยังเปิด | รหัสและระดับความรุนแรง |
| ผู้อนุมัติรับมอบ | ชื่อและวันที่ |

## 9. การจัดการการเปลี่ยนแปลงและความเสี่ยง (PM.CONTROL)

### 9.1 Change Request ขั้นต่ำ

ทุกคำขอต้องระบุ: รหัสคำขอ, ผู้ขอ, เหตุผล, requirement ที่ได้รับผลกระทบ,
ผลกระทบต่อโค้ด/schema/ความปลอดภัย/กำหนดส่ง, แผนทดสอบ, ผู้อนุมัติ, วันที่ และสถานะ
`เสนอ -> วิเคราะห์ -> อนุมัติ/ปฏิเสธ -> พัฒนา -> ทดสอบ -> ปิด`

### 9.2 ทะเบียนความเสี่ยงเริ่มต้น

| ความเสี่ยง | ระดับ | การควบคุม/แผนสำรอง | เจ้าของ |
| --- | --- | --- | --- |
| ฐานข้อมูลหรือไฟล์สลิปสูญหาย | สูง | สำรองฐานข้อมูลและ `server/storage` ร่วมกัน และทดสอบกู้คืน | Operations |
| จองซ้อนหรือราคาถูกแก้จาก client | สูง | transaction, server-side pricing และ concurrent tests | Developer |
| รับชำระเงินจริงแต่ระบบไม่พร้อม | สูง | ให้แอดมินอนุมัติเปิดรับจองหลัง end-to-end test และตรวจยอดจริงเอง | Business Owner |
| session/config ตั้งค่าไม่ปลอดภัย | สูง | ใช้ HTTPS, secure cookies, config นอก web root และ checklist ติดตั้ง | Operations |
| กล้องหรือ browser จริงทำงานต่างจากการทดสอบ | กลาง | มีทางกรอกรหัสตั๋วสำรองและทดสอบบนอุปกรณ์จริงก่อนเปิดใช้ | Tester |
| maintenance ไม่ทำงานตามเวลา | กลาง | API ตรวจซ้ำและตั้ง cron ทุกนาที พร้อมตรวจ log | Operations |

## 10. การจัดการ configuration และ release

- Source of truth ของซอร์สคือ Git; branch/commit ที่ปล่อยต้องระบุใน release record
- ห้าม commit `server/config.php`, credentials, `.env.local` หรือไฟล์อัปโหลดจริง
- schema ใหม่ต้องอยู่ใน `database/` และต้องอธิบายลำดับการรันใน README
- release ต้องมี build ที่สร้างแล้ว เอกสารติดตั้ง และผล test ของ commit เดียวกัน
- ก่อน deploy ให้สำรองฐานข้อมูลและ `server/storage`; หลัง deploy ตรวจ login, API health,
  สร้างรายการทดสอบ และ maintenance

## 11. ตัวชี้วัดและการทบทวน

PM ทบทวนเมื่อจบแต่ละรอบหรืออย่างน้อยทุก release และบันทึกค่าเหล่านี้:

- อัตรา test ผ่าน = test ที่ผ่าน / test ที่รัน
- จำนวน defect แยกตามระดับและเวลาที่ใช้ปิด
- จำนวน Change Request ที่อนุมัติ/ปฏิเสธ และผลกระทบต่อกำหนดส่ง
- จำนวน incident หลังปล่อย เช่น จองซ้อน ชำระเงินผิดสถานะ หรือเช็คอินซ้ำ
- ผลการสำรองและการกู้คืนล่าสุด

เกณฑ์เตือน: มี defect สูงค้างก่อนปล่อย, test ผ่านต่ำกว่า 100% ของชุดบังคับ,
ไม่มีการสำรองที่ตรวจสอบแล้ว หรือมี requirement ที่ยังไม่มีหลักฐาน verification/acceptance
ให้ PM หยุดการเปิดรับจองและทบทวนก่อนปล่อย

## 12. Definition of Done

งานหนึ่งรายการถือว่าเสร็จเมื่อ:

- ข้อกำหนดและ acceptance criteria ได้รับการยืนยัน
- โค้ด/SQL/เอกสารถูกทบทวนและไม่มี secret ปะปน
- test ที่เกี่ยวข้องผ่าน รวมกรณีผิดพลาดและสิทธิ์
